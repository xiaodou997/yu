## 2. 分层定位

临时诊断将 SVG 输出、纹理上传、GPU 渲染目标、drawable 和实际呈现分开。失败轮上传前的 50×38 公式位图有185个明显非透明像素；GPU 渲染目标和复制后的 drawable 都有175个深色像素，命令完成且无 API 错误。实际窗口可见、未最小化且为活动窗口，Swift 的图层身份与提交的 YuMetalLayer 相同。

`dropped-repeat-1` 的冷启动图层随后明确收到连续三个 `presentedTime=0` 的呈现回调，包含最后的公式帧。Apple 的 `MTLDrawable.presentedTime` 契约将0用于尚未呈现或帧被丢弃；这里观察的是回调已经执行，而不是在提交后立即读取尚未完成的时间。旧代码在回调中直接忽略非正时间；资源已经完成、逻辑帧已经标为提交，因而没有新的渲染请求恢复末帧。

这定位的是应用没有处理末帧呈现丢弃的缺口，不声称解释所有系统合成器丢帧原因。参考 Apple `MTLDrawable.presentedTime` 文档及测试机 Metal SDK 的 `MTLDrawable.h`。

## 3. 保留与拒绝的改动

保留的实现：原生回调只接受当前提交序号、当前绑定／尺寸代际的显式丢帧，向主线程发送带原图层身份的通知；新的提交、成功呈现、尺寸变化、解绑及重复旧回调均拒绝。Swift 仅为仍绑定、可见、未睡眠的相同图层申请恢复，使用既有视图绑定 CADisplayLink 的一次性显示节拍，再走保留渲染计划的提交路径。正常内容／窗口请求取消旧恢复并重置预算。每个预算最多8次，同一待处理显示节拍合并，超限记录错误，等待新的正常请求；没有后台轮询或无限提交。

失败尝试保留为负证据：调整 layer 挂接顺序仍在第七次重开出现空白，已撤回；仅增加即时主队列恢复的带诊断候选虽然连续8次通过，移除诊断后 `final-light-2` 仍为三次0像素，因此即时恢复没有被认定为完成修复。随后恢复请求改为显示节拍触发，不用任意睡眠、GPU 等待或窗口尺寸变化获得通过。

所有临时 CPU／图层打印和生产路径 GPU 读回已移除。公式解析、着色器、顶点批处理、纹理模式、资源缓存策略和编辑历史不变。单独 GPU 像素回归中的读回／等待只由测试调用，不进入产品帧提交函数。
