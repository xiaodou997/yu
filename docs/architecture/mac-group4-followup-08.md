## 3. 历史接收审计的实际验证

接手提交的审计只对显式启用 `YU_HISTORY_AUDIT=1`、带 32 位十六进制隔离后缀的资源／嵌入检查应用生效。记录字段仅包含进程、窗口编号、入口、命令、事件时间、第一响应者／可编辑／预编辑／命令可用状态和执行前后 revision；不记录文档路径、全文、选中文字或输入字符。每个进程最多 4096 次配对记录，耗尽、缺失或坏记录不能被解释为完整诊断。

本次独立的四文档诊断场景取得 **38 对完整接收记录**：21 次撤销、17 次重做，均从 `keyEquivalent` 入口被处理并改变 revision。原源码、历史、保存、同进程和新进程重开检查完成。它证明这些操作被产品入口接收，不证明上轮偶发未生效事件走过哪个入口；没有记录也不能反推事件未投递。

该场景同时启用了分配栈，明确标为诊断实验，不能与无诊断的长时物理足迹直接比较。普通浅深色长压力不启用历史接收日志。

## 4. 首次取得实际产品分配栈：有限归因结果

`allocations-60-light` 使用相同主程序、4 个工作文档和 1 个保活窗口，请求 60 秒，实际完成 3 轮／71.431 秒压力，整个原生流程为 313.479 秒。只在该隔离进程启用 MallocStackLogging，分别在所有窗口刚打开、保留原历史空闲后、关闭工作文档并空闲后执行 `heap -sortBySize -noContent`、`malloc_history -allBySize` 和 `leaks -noContent`。每次采样前后核对进程创建身份。终点浅色公式截图已实际复核，进程正常退出。

下表是系统 heap 报告中的**已分配堆字节**，不是应用物理足迹、显存或泄漏字节。逐行聚合后的节点数和字节数与三份报告总计完全一致。同一阶段的各工具依次执行，并非同时刻的原子普查；分配栈用于定位分配来源，不作为物理内存的精确分摊。

分配栈把场景向量定位到 `macos_new_frame_worker → ViewportFrameBuilder::publish_owned_document_cancelable → ViewportFramePublisher::publish_with_resources → append_editor_decorations → SceneBuilder::push → RawVec::grow_one/realloc`。保留历史采样中该主调用栈为 5 次分配、10,592,256 字节。代码中 SceneBuilder 持有 Vec，并在 finish 时交给 Scene；这提供具体保留位置，但不是无限增长的证明，也没有据此修改渲染器或减少选区／光标功能。

字形图集的 `AtlasPage::copy_bitmap` 主栈显示 4 次、16,842,752 字节，代码中对应 `Arc::make_mut`。同时 `AtlasPage::new` 的分配减少；把两者及小对象合计后，前两阶段 backing 总量均为 21,053,680 字节。**不能只报告 copy_bitmap 新增约 16.8 MB 而漏掉 old backing 的减少，然后误判为额外泄漏。**

### 非零 leaks 结果仍然保留

三次 `leaks` 均退出 1，各报告 **294 个节点、19,312 字节**。根循环类型为 3 个 NSXPCConnection，分配栈涉及 AppIntents 的 LNProcessInstanceRegistryClient 和 LinkServices 的连接创建；该总量在压力前就存在，关闭文档后没有变化。

这份有限报告没有解释多 MB 的增长，也不足以认定是普遍系统缺陷或误报。它明确**不是零泄漏结果**：原生测试流程退出 0 只代表编辑／历史／重开等检查完成，不能把三次扫描退出 1 写成泄漏检查通过。堆对象、虚拟映射和物理足迹继续分开记录，不把这次短诊断的 8.94 MB 当作旧版本或长压力中增长的完整解释。
