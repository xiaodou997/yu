## 2. 实验问题与固定范围

问题不是“再多跑半小时”，而是充分预热后，同一个进程反复关闭四个工作文档，仅剩同一个未编辑保活窗口时，驻留是否继续逐轮抬升。

新增 `run-resource-residency.py` 复用既有 NativeSoak 的隔离应用、原生输入、完整源码／BOM／CRLF、进程创建身份、资源门禁、关闭及清理。原 runner 仅提取原本相同的应用环境构造方法，默认行为不变；新 runner 在子进程环境中去除分配注入／僵尸对象／历史日志开关，普通场景不附加分配工具。

固定负载为四个文档、四个生命周期，每个生命周期三轮有效资源→错误资源→普通内容。各轮使用相同生成代数范围和文件身份，关闭后重开真实保存字节，不重新写入较小文档。保留原历史空闲70秒，验证每文档9条undo／0条redo及真实撤销重做后正常关闭；再对原保活窗口空闲70秒。每轮核对同一进程创建身份。没有清历史、清缓存、调用内存压力或重启来压低比较基线。

普通实验与 `--allocation-stacks` 独立实验串行执行，不能争用桌面。后者仅对隔离应用启用分配栈，第一次和最后一次闭窗空闲后分别采样 heap、分配栈、leaks、vmmap；这些工具顺序执行，不是原子普查。leaks 的非零状态单独保留，不因原生流程通过而升级为零泄漏。

最后新进程冷重开仍使用原来的公式像素／外观门禁，并检查编辑、撤销重做及保存；此新进程样本不参与同进程驻留基线比较。

结果、失败栈、源码差异、原焦点快照、压缩事件／应用日志和该次测试脚本快照保存在 `evidence/group4-followup-20260927-09/initial-baseline-failed/`。此运行不能用于闭窗后的驻留结论。

### 修正测试工具的临时剪贴板生命周期，不改产品

旧驱动的paste-text在发送一次Command-V后固定等待0.3秒便恢复原剪贴板。调用方再等源码变化时，临时输入可能已经失效。新增显式paste-document模式只接受全文选区和不同的目标源码，在原来的单次按键后最多只读等待5秒；看到精确目标源码才释放临时剪贴板，否则失败，不重发按键。普通压力循环和产品源码均未改；驻留runner仅在已知全文替换的install中使用该模式，源码身份日志继续脱敏。

`check-native-paste-lease.py` 的独立AppKit消费夹具延迟0.9秒读取剪贴板，确定性对照结果：旧入口只发送一次粘贴却读到了PRIOR_PAYLOAD；新入口同样只发送一次，等待约0.817秒后读到AFTER。新入口通过只证明这个测试工具的生命周期缺口得到修正，**不证明它就是此前真实产品粘贴失败的唯一原因**。结果为 `paste-lease-regression.json`，它不是Yu产品验收。

夹具早期也有两份失败记录：第一份错误调用NSTextView便利初始化器导致崩溃，并且当时已替换测试剪贴板，原剪贴板未自动恢复；没有记录原内容，无法从证据找回。第二份缺少文本存储，未产生输入即失败，正常退出。最终夹具改用完整文本存储和指定初始化器，并在借用剪贴板前构造文本视图；失败结果原样保存，不混入成功数量。正式驻留原生应用没有因此重新构建。

逐行解析两份heap报告，节点与字节合计分别与原报告完全一致。下表是**已分配堆字节**，不是物理足迹或泄漏量；所有工具为顺序采样。

这两次同保活状态的净堆增量为189,152字节，增加1,514个节点；上述主要产品类别数量／字节没有随工作文档开关累积。分配栈仍定位到RenderPlanBuilder、AtlasPage及SceneBuilder相关路径，保留了原报告行号和调用栈摘录。**这是一段有限生命周期证据，不是所有产品对象均已穷尽审计，也不是全局无泄漏证明。**

同一诊断的vmmap显示：malloc zone已分配量约33.6M→33.8M，而dirty约100.3M→62.4M，报告碎片量约66.7M→28.6M；第一份报告还有约50.9M的Malloc Large(empty) dirty与38.8M的Malloc Small(empty) dirty。报告同时列出约64.2M的Performance Tool Data。它们为“堆对象字节与足迹不是同一指标”提供具体证据，但这些类别不能与heap重复相加，工具显示单位和舍入也不等于精确逐字节分账。

未分类的4,194,304字节在两次heap中均保留，但对应vmmap zone两次resident／dirty均为0K。因此不能把这4MB逻辑分配直接认作4MB物理驻留；具体对象归属仍未确认。malloc_history最大项还包含字体文件的mmap映射，例如192,135,168字节的字体映射，不是192MB堆泄漏。摘录显式区分映射与malloc分配，不将总栈字节等同物理足迹。

两次leaks均退出1，均报告416节点／26,400字节，根循环为3个NSXPCConnection，栈经过AppIntents的LNProcessInstanceRegistryClient与LinkServices。数量未随这三次追加开关增长，但它仍是非零报告，不认定为系统误报，也不拿它解释几十MB驻留。

结论：本批已把部分驻留拆成有限产品对象保留、分配器映射／碎片及诊断开销，未观察到所列主要产品对象的逐轮累积；普通场景的剩余71.55MB与较大波动尚未完整归因。第一／第四堆样本、vmmap和分配栈均来自独立诊断，不能用来精确分摊普通场景或上一轮30分钟中的每一MB。证据包括 `diagnostic-heap-analysis.json`、`diagnostic-stack-excerpts.json` 和带哈希的原始工具报告。没有因此修改产品渲染或历史实现。
